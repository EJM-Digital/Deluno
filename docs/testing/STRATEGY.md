# Deluno testing strategy

The bar, in the owner's words (14 Oct 2026): "robust full 100% app testing coverage, no gaps in testing at all... every screen, every
menu, every snippet of code, every function needs to have a test and be proven to work... designed in a way that a senior software
development team would do and do better." Weir holds the same bar. Both apps use one register format, and the calls between them use
shared `contract.*` ids.

"Covered" means all seven measures below hold together. Any one of them alone can be gamed: a line can be run by a test that asserts
nothing, and a behaviour can be listed without being proven. So no single number counts as coverage.

## The seven measures, each enforced in CI

| # | Measure | What it proves | Tool | Gate |
|---|---|---|---|---|
| 1 | **Behaviour register**: every screen, menu item, setting, API route, job, migration, integration operation, failure mode, tray action and install/update path has a row, and each row names the tests that prove it | nothing the app does is unlisted, and every listed thing is proven at its level | `docs/testing/coverage-register.json`, `scripts/check-coverage-register.mjs` | unmapped item, missing test or a rise in the gaps (against the base branch) fails now; any gap fails once `--strict` is on |
| 2 | **Line and branch coverage**, measured for every production assembly and module | every line and every branch of code runs under a test | coverlet (all .NET test projects), v8 (vitest, Node scripts), merged per file | a per-file ratchet that never goes down, ending at 100%; every exclusion is listed with a reason. Async method, iterator and lambda bodies count: `CompilerGeneratedAttribute` is not excluded (#1450) |
| 3 | **Mutation score**: the tests fail when the code is deliberately broken | the tests assert, they don't just run | Stryker.NET, StrykerJS | weekly and by hand, never a gate; a per-project threshold that ratchets up |
| 4 | **End to end per screen and menu**: every screen and every menu or drawer action through the browser against the real Deluno server, with the calls it depends on not stubbed | the screens work with the real backend | Playwright, plus a guard that rejects `page.route` and `serveLive*` in specs marked real | each screen route and menu action in the inventory has a real spec |
| 5 | **Real other apps, real disk, real install**: anything that talks to another app, changes files on disk, or installs, updates or runs the tray | the app works with the real world, not with our guess of it | golden-VM scenario suite (each scenario runs alone), recorded real replies (`tests/fixtures/recorded/`) with a freshness check, and `real-fs` backend tests (real files in a real temp folder, a real SQLite file) | the row's `touches` decides it: other-app, disk and install rows need one of these; `real-fs` (below) satisfies disk and install rows, but never a row marked `vm` |
| 6 | **Properties**: parsers, matchers, quality and custom-format scoring, naming templates, path mapping, release-name and episode parsing hold for generated inputs, not only the examples someone thought of | edge cases nobody wrote by hand | FsCheck, fast-check | each listed module has property tests |
| 7 | **Determinism**: every test passes or fails the same way on every run | a red result is a real defect, and a green one is real proof | static check: no fixed sleeps without a reason, every wait bounded and on an event; nightly repeat of each suite N times | a flake is a defect with an issue, never a retry or a quarantine |

### Measure 3: how mutation testing runs (issue 1269)

- **Tools, pinned:** Stryker.NET in `.config/dotnet-tools.json` (`dotnet tool restore`), StrykerJS in the root `package.json`. One `stryker-config.json` sits beside every production `.csproj` (generated by `scripts/mutation/gen-stryker-configs.mjs` from the project reference graph, so each points at the test projects that cover it; `--check` runs in CI). `apps/web`, `sdk/typescript` and `services/metadata-gateway` each have a `stryker.config.json`. Run Stryker.NET from the repository root, where it finds `Deluno.slnx` and analyses it as a solution (most production projects are referenced by a test project only through another project, which Stryker.NET reaches in solution mode only; analysing 30 projects needs a machine that is not already busy): `dotnet tool run dotnet-stryker -f src/<Project>/stryker-config.json`; the web app: `npm run mutation` in `apps/web` (StrykerJS runs the whole web test suite once for coverage first, so a one-folder run still takes minutes; add `--mutate "src/lib/**/*.ts,!src/**/*.test.ts"` for one folder).
- **Changed files, by hand (`node scripts/mutation/run-changed.mjs --base <sha>`; no CI job runs it, the owner, 7 Nov 2026):** `scripts/mutation/run-changed.mjs` mutates only the changed lines: StrykerJS gets each changed file's added or altered line ranges (`file:start-end`, from `git diff -U0`), so a small fix in a large file answers for its own lines, not for every old line of the file (29 Oct 2026). Stryker.NET uses its diff mode (`--since:<base sha>`, the pull request's base or the commit before the push) for each production project whose source changed; StrykerJS has no diff mode, so the changed web, sdk and gateway source files go to `--mutate`. `scripts/check-mutation-ratchet.mjs --survivors` then fails on a mutant that survived or was never covered only when it is in a risky area (`docs/testing/mutation-risky-areas.json`: imports, deletes, download clients, the processor hand-off, files on disk; the owner's scope change of 6 Nov 2026), unless `docs/testing/mutation-equivalents.json` lists it with the reason. Survivors elsewhere are printed as notes and uploaded in the report; the score of their project is published by the whole-project run and may only go up. The Windows-only tray is left to the whole-project run.
- **Whole projects, weekly and by hand (`mutation-nightly.yml`, Saturday 11:17 UTC and `workflow_dispatch` with scope `risky` or `all`; the owner, 7 Nov 2026). No mutation run or score gates anything: not releases, `ci-passed` or branch protection. Every surviving mutant or floor drop from the weekly run is raised as an issue and fixed during the week, and the next weekly run checks those fixes:** the run, one job per .NET production project and one per JavaScript project, at most 6 at once (4 .NET, 2 JavaScript), each independent: a project that times out or a cancelled run still uploads every report that was written, and the score job scores what finished, on the runners `ci.yml` uses (`DELUNO_LINUX_RUNS_ON` and `DELUNO_WINDOWS_RUNS_ON`: free self-hosted runners while the repository is private, GitHub-hosted and free once it is public). The score per project and every surviving mutant go to the job summary; the run fails when a project falls below `docs/testing/mutation-thresholds.json`, and it uploads the raised thresholds it would write (`--update`) for the owner to review and commit. The thresholds only go up (`node scripts/check-mutation-ratchet.mjs --reports <dir> --update` never lowers a number, and the unit test of the ratchet holds it to that). **The one mutation-related check CI runs** (`repo-checks`) never runs mutation and gates on no score; it only stops a floor being lowered without a reason given in that same change (a `lowered` entry already at the base excuses nothing, and `--update` clears the entries): `node scripts/check-mutation-ratchet.mjs --base <previous commit>` fails a change that lowers or removes a floor in `mutation-thresholds.json` unless that change adds a top-level `"lowered": {"<project>": "<reason>"}` entry for the project (reason of at least 20 characters). A missing or unreachable base passes.
- **Weekly repeat (`repeat-nightly.yml`, Friday 11:17 UTC, Friday night in Sydney):** each backend test project, the web unit tests, and the Node tests (scripts, metadata gateway, sdk) run three times in a row, and the Playwright smoke shards twice, on one build, with no retry, at most 6 jobs at once (3 backend projects with the web and Node jobs, then the 3 shards). The scenario suite's offline checks are not repeated: they read files and give the same answer every run, and `ci.yml` runs them on every push. The first failing run fails the night, and the `report` job opens a defect issue. The end-to-end groups are not repeated: each is a scenario run of many minutes, and the golden-VM suite repeats them before every tag. Every job gets its own temp folder (`TMPDIR`): runners share one machine, and a fixed `/tmp` folder made by one runner's user is closed to the next.
- **Weekly freshness (`freshness-nightly.yml`, Friday 10:47 UTC, Friday night in Sydney):** `scripts/check-recording-freshness.mjs` compares the newest version recorded for each app with the app's newest GitHub release and opens one defect issue naming the apps whose recording is a major version, or more than one minor version, behind (while that issue is open, a later night comments on it with the run link instead of opening another; `scripts/report-nightly-issue.mjs`, which the nightly repeat uses too). Services recorded by date (TMDB, TheXEM, Gestdown, GitHub) and Deluno's own side of Weir are not versions to keep up with.
- **Waits (measure 7):** `scripts/check-coverage-register.mjs` fails on a wait that is not bounded or not named: a call to `Wait.UntilAsync` (or a test file's own helper of that name) names what it waits for; a limit of its own carries a `// reason:`; a helper written in a test file has a limit; `until()` in the end-to-end suite names what it waits for and gives its seconds; `Wait-Until` in the golden-path suite sets `-TimeoutSec` (held by `Test-ScenarioSuite.ps1`); a `while (true)`, `for (;;)`, argument-less `.Wait()` or `WaitForExit()`, or `Timeout.Infinite` carries a `// reason:` saying what ends it. The default `Wait.UntilAsync` limit is 10 s and is the helper's one documented bound.
- **The score** is (killed + timed out) / (killed + timed out + survived + not covered). **Equivalent mutants** are those no test can tell from the original code; each entry in `mutation-equivalents.json` names the project, file, mutator, line and replacement, and gives the reason. A line that moves makes its entry stale, and the mutant fails the next push until the entry is corrected, which keeps the list honest.

### Measure 5: how disk and install behaviour is proven (owner, 15 Oct 2026)

- **`real-fs`** is a backend test that runs Deluno's real code against real files on the real file system (a temp folder; real hard links, moves, deletes, permissions) or a real SQLite database file (migrations, upgrades from released versions), with no mocked file system or storage. It satisfies `real` for a row that touches `disk` or `install`. The register check verifies the claim statically (the test or its class setup creates the temp folder or database, works on it, and names no fake or in-memory file system or store); if it cannot decide, the claim is refused, the row stays `inproc`, and the refusal is counted.
- **`vm: true`** marks a row that only a real install can prove: NTFS-specific behaviour (alternate streams, case rules, long paths, ACLs), network shares (UNC/SMB/NAS), cross-drive or cross-volume moves and hard links, the installer, the update, the tray and Windows service mode. Such a row needs a `scenario` proof; `real-fs` does not satisfy it.

The supporting checks: every migration is tested from the previous schema with real data in it; every route answers 401 or 403 for a
missing or wrong credential (generated from the endpoint map); accessibility (axe) on every screen; and the Deluno–Weir contract is
replayed on both sides from the same recordings.

## Tiers

- **Every push (CI):** build; measures 1, 2 and 7's static checks; unit, in-process and property tests; the Playwright real specs;
  recorded-reply replays. A push that changes code always runs both the backend and the web tests,
  so coverage (measure 2) is measured on every code push; a documents-only push runs only the repository checks. The register check
  runs with `--strict` once the repository variable `DELUNO_REGISTER_STRICT` is `true`, which is set when the last gap issue closes. Rows that need an outside account the owner does not have are the one exception (the owner, 31 Oct 2026): they are marked `waived`, are not gaps and do not block `--strict`, but are counted and listed apart and in `docs/testing/account-requests.md`, so they stay visible until an account exists and they are proven.
- **When an area's coverage issue closes (the owner, 29 Oct 2026):** once every high and medium row of the area reaches its
  required level. Its low rows are carried by the one sweep issue (#1329), rows that need an outside account by #1343, and rows
  that need a golden-VM scenario by #1278. Line and branch coverage and the mutation score are measured app-wide and carried by
  #1268 and #1269, not by each area's issue.
- **On weekend nights in Sydney, on the same runners as CI (the owner, 30 Oct 2026):** Friday, recording freshness and the weekly repeat; Saturday, the weekly mutation run; Sunday, the dependency audit. Repeat runs at most 6 jobs at once, leaving the rest of the organisation's 20 hosted runners for other repositories. Mutation (`mutation-nightly.yml`) runs weekly and by hand and gates nothing. Every suite repeated to catch flakes
  (`repeat-nightly.yml`); recording freshness against the newest version of each app (`freshness-nightly.yml`).
- **Before a tag:** the full golden-VM scenario suite on the exact commit. It is the final proof, not the place where bugs are found.
  A gap found there is a gap in measures 1 to 6, and gets a test at the lowest layer that can catch it.

## How a gap is closed

1. Its register row names the test to write and the proof level it needs.
2. The test is written to fail first, against the real code. For another app, it uses that app's recorded reply.
3. The row's `proofs` gets the test. The check confirms that the test exists and reaches the level.
4. The coverage and determinism gates pass for the files it touches.
