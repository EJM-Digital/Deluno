# Coverage register

The owner's bar is that no behaviour of Deluno goes untested. This page and `coverage-register.json` make that a number
that a script checks, instead of a claim.

## How to read the register

`coverage-register.json` has one row per behaviour a person or another app can rely on: a screen action, a state, an API
route, a job, an integration operation, a failure mode, a migration, an install or update step, a tray action. Each row has:

| Field | Meaning |
| --- | --- |
| `id` | Stable, `area.screen-or-subsystem.behaviour-slug`. Never reused. |
| `area` | One of the register's `areas` (a screen group, `api`, `services`, `health`, `migrations`, `integrations`, `platform`, `web`, `scenarios`). |
| `behaviour` | The behaviour in one plain sentence. |
| `kind` | `screen action`, `state`, `API route`, `job`, `integration-operation`, `failure-mode`, `migration`, `install-update` or `tray`. |
| `severity` | `high` (data loss, wrong file or media handling, security, or a main flow: add a title, search, grab, import, remove), `medium` (a feature not working) or `low` (cosmetic). |
| `required` | The proof level the row needs: `real` for every high row, at least `inproc` for the rest. |
| `proofs` | The tests that prove it: `{ "type", "file", "name" }`. **Empty when the row is a gap.** |
| `covers` | The inventory keys the row accounts for (see below). |
| `partial` | Tests the audit found that touch the behaviour but do not prove it. Not counted; kept so a gap shows where to start. |
| `needs` | For a gap: the kind of test the audit suggested to close it. |
| `audit` | Where the row came from (the audit of 14 Oct 2026, or the inventory). |

A proof's `type` is one of `vitest`, `smoke` (a Playwright spec), `backend` (an xUnit or node test), `scenario` (a golden-path
scenario on the golden VM) or `recording-replay` (a test that replays the other app's recorded real reply from
`tests/fixtures/recorded`). Its `name` is a test, a test group or a class in `file`; `"*"` means the whole file.

## Proof levels

- **real**: a `scenario`, or a `recording-replay`. Something other than Deluno's own assumption of how the other app answers.
- **inproc**: a `vitest`, a `smoke` or a `backend` test. It runs Deluno's code, but the other side is Deluno's own stand-in.
- **none**: the row is a gap.

A row is **proven** when its best proof reaches `required`. A high row is therefore not proven by an in-process test, however good.

## The rules

1. **Everything is mapped.** `scripts/coverage/inventory.mjs` reads the source for every API route (each `Map*` call), web route
   (`apps/web/src/router.tsx`), hosted service, job lane, job handler, system task, health check, migration, integration client and
   operation, tray menu action and golden-path scenario id. Every item must be in the `covers` of some row. New code does not
   arrive unmapped: CI fails (`scripts/check-coverage-register.mjs`), and `--stubs` prints the rows to add.
2. **Every proof exists.** The file is in the repository, the name is in the file, and the type is true of it (a
   `recording-replay` test really loads a recording, a `scenario` is a `.ps1` scenario). A renamed or deleted test fails CI until the row is fixed; the row is then a gap again.
3. **Gaps are counted, not yet failed.** A row below its required level is a gap. Today the register is far from complete, so gaps are
   reported as a total and `--strict` fails on any. When the gaps are closed, CI runs `--strict`.
4. **Determinism.** No fixed `Start-Sleep`, `Task.Delay`, `Thread.Sleep` or `waitForTimeout` in a test without a `// reason:`
   (`# reason:` in PowerShell) comment on its line. Every golden-path scenario is runnable alone (registered under its own id in
   `ScenarioPlan.ps1`, with a defined group function). Every test of an external app is on a recording or listed in
   `tests/recorded-reply-allow-list.json`. Reported with counts; `--strict` fails on any.

## Commands

```
node scripts/check-coverage-register.mjs               # the check CI runs; (a) and (b) fail it
node scripts/check-coverage-register.mjs --strict      # also fails on any gap and any rule breach
node scripts/check-coverage-register.mjs --list-gaps   # every gap, high first
node scripts/check-coverage-register.mjs --stubs       # row stubs for inventory items with no row
node scripts/check-coverage-register.mjs --write-doc   # rewrites the totals below
node scripts/coverage/inventory.mjs --list             # the inventory
node --test scripts/check-coverage-register.test.mjs   # the check's own tests
```

When you add a route, screen, job, migration, integration operation, tray action or scenario: add its row (with the key in `covers`
and, if a test proves it, the proof) in the same change. When you add a test that proves a gap, put it in `proofs` and the gap closes.
